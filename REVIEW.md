# REVIEW.md

The following issues were verified against the application during implementation. Reproductions were added to the test
suite before the corresponding fixes.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `PunchInIn`, `PunchOutIn`, `RegularizeIn` | Pydantic's non-strict integer fields accepted integer-looking strings and whole-number floats for epoch milliseconds, although the contract rejects strings and all floats. | Send `"punched_at": "1783309080000"` or `"punched_at": 1783309080000.0`; the original endpoint returned 201. | Changed timestamp fields to `StrictInt`; non-integer JSON types now receive 422. |
| 2 | `punch_out` | It selected the most recent punch-in even when that instant was later than the requested punch-out instant. | Create an open record for the next day, then punch out an earlier open shift; the original endpoint selected the future record and returned 422. | Bound the candidate query by `punch_in <= punched_at`, preserving the 422 response when punch-out is before the only punch-in. |
| 3 | `EmployeeIn`, attendance date filters, regularization path, trend query | Date format patterns alone accepted impossible dates such as `2026-02-31`. Some paths could then reach an uncaught `ValueError`. | Submit `2026-02-31` as `joined_on`, a filter date, a correction date, or the trend's `from`; the original behavior included 201, 200, 404, or an exception instead of 422. | Added calendar-date parsing and validation at these API boundaries. |
| 4 | `regularize_attendance` | Its update was atomic as a single MongoDB operation, but the filter only used `_id`; a correction computed from an old read could overwrite a concurrent correction's fields. | Inject a competing status update after the initial read; the original request returned 200 and replaced the competing status. | Added the previously read state to the conditional update filter and return 409 when that state has changed. The audit history is appended only if the compare-and-set succeeds. |
| 5 | `create_indexes` | A broad exception handler printed index-creation failures and let startup continue, even though unique indexes are required for correctness and concurrency. | Make an index-creation call raise; the original function swallowed the error and continued. | Removed the catch and module-import index creation. Indexes are created during FastAPI startup; failures now propagate and prevent a false-ready startup. |
| 6 | `explain_endpoint` | The attendance-list explain accepted status values rejected by `/attendance`, and the trend explain accepted ranges longer than the endpoint's 92-day maximum. | Request `status=UNKNOWN` or a 93-day trend range; the explain route originally returned 200 instead of 422. | Applied the corresponding endpoint validations before building the explain command. |
| 7 | API response formatting and generated OpenAPI | Seeded attendance documents may omit punch fields and derived defaults; responses omitted contract-required fields. Auto-generated operation IDs and undocumented response models/statuses also differed from the contract. | Read seeded records with missing `history` or absent punch values; required response keys were missing. Compare `/openapi.json` operations with the supplied contract. | Fill documented defaults at the response boundary and add response models, exact operation IDs, error responses, and contract-schema tests. |
| 8 | `create_indexes` / department summary explain | An unfiltered department summary used a collection scan on employees when selecting those who joined by month end. | Explain `department_summary` without a department filter on a 100,000-log dataset; the employee-side plan contained `COLLSCAN`. | Added an index on `employees.joined_on`; the unfiltered 100,000-record explain then included `IXSCAN` and no `COLLSCAN`. |
| 9 | Department trend moving-average pipeline | It averaged unrounded daily attendance ratios, then rounded the average. R8 requires each daily attendance rate to be rounded before that rate enters the moving average. | Rates of 0 and 1.5/7 produce a required two-day average of 0.1072, while averaging raw ratios gives 0.1071. | Round each eligible daily ratio half-up inside the aggregation before `$setWindowFields`; the explain pipeline uses the same expression. |
| 10 | Optional timestamp and correction request fields | Optional Pydantic fields also accepted explicit JSON `null`, though the contract permits omission but does not mark these values nullable. A null punch field could be treated as omitted during a correction. | Send `punched_at: null`, or set `status: ABSENT` with `punch_in: null`; the values could be accepted as if omitted. | Added before-model validation to distinguish omitted fields from explicit nulls and return 422 for nulls. |
| 11 | Monthly and department trend date boundaries | Valid inputs at the end of year 9999 overflowed when computing the next calendar day/year. | Request monthly analytics for `9999-12` or a department trend for `9999-12-31`; the original code raised an uncaught date overflow. | Calculate month ends without advancing into year 10000 and use an end-of-day exclusive trend bound, which includes the final date without overflowing. |

## Validation performed

Regression tests for the issues above, hand-built analytics edge cases, helper behavior, and the existing endpoint suite pass
against a disposable MongoDB database. All five explain plans were checked against a generated 100,000-record dataset;
each included `IXSCAN` and none included `COLLSCAN`. This local synthetic check does not guarantee the same plans for
every production workload or the evaluator's hidden dataset. Parallel HTTP requests were tested for duplicate employee
creation, duplicate punch-in, simultaneous punch-out, and concurrent regularization.
